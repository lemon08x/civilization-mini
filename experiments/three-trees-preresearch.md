# 学科、产品、系统三类升级树预研

后续实施状态：0.19.0已落地学科/产品状态与两个早期系统，详见 [实际规则](../docs/THREE_TREES_V19.md)。后期流水线、无人化仍是预研。下文保留原结构候选，不代表全部已经实现。

原预研状态：结构候选，未接入游戏。基线为0.18.0；本轮只写预研，不修改规则、参数、存档或界面，不执行模拟。本文的劳动报价与数据结构用于检查因果关系，不是已经验证的游戏数值。

结论：建议采用三类树。先把解锁、实物、人员与运行拆开，再扩节点。近期先实现农业供水、机械加工两个最小系统；流水线与无人化先保留明确的接口和准入条件，不一次铺完整后期树。

配套：[两条示例链与静态推演](three-trees-example-chains.md)。

## 1. 现状与要解决的问题

| 当前实现 | 问题 | 建议变化 |
| --- | --- | --- |
| `BranchNode.parents + sample`，学习扣实验样品 | 学科可被商品供应卡住 | 学科前置仅知识节点；学习只花时间、精力，样品移至产品试制 |
| `BRANCH_PRODUCTS / BRANCH_PROCESSES` 只检查知识 | 尚未形成产品研发关系 | 设备与加工部件统一有产品定义、前置产品和验证方式 |
| `ProductSpec.from` 是说明关系 | 不能直接变成硬门槛；例如磨粮不应先经过脱粒设备 | 逐项判断真实技术依赖，另建明确的前置字段 |
| 本人完成配方产生 `protocols`，设备制造只产生建造事件 | 设备和部件的验证、传承口径不统一 | 产品验证记录与制造规程分开建模 |
| 泵按条件自动生效，发电依赖当前经营者L6 | 自动执行与人力需求混杂 | 效果由系统实例运行产生，检查岗位、设备和资源 |
| O0/O1/O2映射回组织等级，经营安排是一组开关 | 系统间没有统一前置和劳动预算 | 系统定义、实例配置、岗位任务与运行状态独立 |
| 雇员每季一次工作，本人用时间和精力 | 无法表达兼职和流水线省人 | 统一任务需求；对各参与者预留时间、精力与岗位能力 |

既有证据见 [0.18报告](branch-v18-report.md)：知识树变浅后，生活支出和资金积累仍拖慢路线。这只能作为问题线索，不证明三类树或新劳动模型一定改善体验；不重写旧报告或刷新其指纹。

## 2. 三类树的依赖规则

| 类型 | 允许的解锁依赖 | 不允许作为解锁依赖 |
| --- | --- | --- |
| 学科节点K | 本人掌握的前置K | 产品、系统、材料、渠道、地区等级、生产次数 |
| 产品节点P | 前置P验证记录；本人的所需K | 系统运行、系统等级、人物年龄、全树进度 |
| 系统节点S | 所需K、P验证记录、前置S调试记录 | 模糊文明等级、未列明副本进度 |

“学科解锁”统一解释为已经学会；仅满足前置、按钮变亮不算掌握。“前置产品完成”采用上一轮提出的已验证记录，不能只看目录解锁，否则产品树变成知识树的空壳。

首版前置列表全部为AND，空列表表示无该类前置，不要求每个产品必有前产品、每个系统必有前系统。只列直接前置，不反复列完整祖先；界面可展开总需求。需要替代技术路线时再显式增加OR，不用一个字符串同时暗含两种含义。

依赖方向只能K→K/P/S、P→P/S、S→S，跨三类合并检查无环。资源流可循环（例如发电系统给自身控制器供电），但解锁不能循环；运行循环要有启动库存或外部启动源。

## 3. 解锁、验证、实物与知识归属

### 学科

个人掌握集合是唯一学习依据。学习消耗时间与精力，保留天赋减免；不再消耗样品、支付教材费或要求找到指定教师。地方基础指导默认可用，教学与家学是可选学习方式，不能成为额外硬前置。移除样品后，家学原先“免样品”的效果作废，候选改为适度减少学习时间；具体幅度另做参数研究，最低仍需学习投入。

### 产品

产品有三个不同状态：可研发、已验证、有实物。已验证意味着形成长期保留的家族技术记录，实物可以卖出、消耗、损坏，不能因此撤销验证记录。重复生产仍消耗配方物资、加工设备容量和劳动，不重复缴首次研发费用。

验证分两种来源，效果要区分：

- 自行制造：先满足前置，再完成实际试制与检验，写入产品验证和可执行制造规程。样品就是试制实际材料，不再额外重复收一套“知识样品费”。
- 外购产品：买到只增加实物；具备该产品规定的知识、前置后，可以对实物进行付出时间/精力和必要损耗的检验，写入产品验证，但不自动取得可批量制造的工艺规程。

候选选择允许检验外购部件，以保留专业化采购路线；本轮不强制从采矿到化工全部自给。检验过程、试制过程不得要求正在解锁的高级系统：密封件可做简单密封检查，轴可做尺寸和传动试验，泵可用人工试抽，不能先造全自动灌溉系统才验证泵。

已解锁与已验证记录属于家族；个人理论不自动传给后代。后代执行既有规程需岗位能力，研发新产品需由一名掌握全部所需K的研发者负责，首版不把多人零散知识自动拼成一个“全知家族”。高级产品的首次试制不能只由未掌握相关知识的雇员代点完成。

### 系统

定义层是方案；实例层是地块或作坊里实际建成、配置好的系统。状态依次为可建设、待配置、待调试、已调试；当前运行状态另列运行、缺人、缺料、缺能、维修、主动暂停。

前置系统检查家族已调试记录，不要求老系统永远开着。如果下游实际需要上游的水或电，应写运行依赖，而不是把“上游正在运行”藏进解锁条件。实物安装、建设费用、调试劳动都发生在解锁之后；一个调试成功记录不是可以无限复制的免费系统实例。

新系统需负责人具备所需知识才能设计调试；既有实例由合格岗位执行，不每季要求当前家主掌握全部原理。这会改变0.18“家主不会L6便停止发电”的判定，必须作为新规则行为明确验证。

## 4. 建议的数据结构

以下为领域层接口草案，不是当前可导入的配置。类型之间用不同ID前缀；物资、配方、任务、岗位和渠道是运行资料，不扩成第四类升级树。

```ts
type KnowledgeId = `K:${string}`;
type ProductId = `P:${string}`;
type SystemId = `S:${string}`;
type PersonId = string;
type Goods = Record<string, number>;

interface KnowledgeNode {
  id: KnowledgeId;
  parents: KnowledgeId[];
  learning: { time: number; energy: number };
}
interface ProductNode {
  id: ProductId;
  unlock: { knowledge: KnowledgeId[]; products: ProductId[] };
  recipeIds: string[];
  validation: { testId: string; purchasedInspectionAllowed: boolean };
}
interface SystemNode {
  id: SystemId;
  unlock: { knowledge: KnowledgeId[]; products: ProductId[]; systems: SystemId[] };
  construction: { goods: Goods; installedProducts: Record<ProductId, number> };
  commissionTaskId: string;
  operationProfileIds: string[];
}
interface TaskSpec {
  id: string;
  qualification: string; // 能执行某规程的岗位能力，不等于完整个人学科
  time: number;
  energy: number;
  inputs: Goods;
  outputs: Goods;
  equipmentSlots: Record<string, number>;
  carryWork: boolean;
}
interface UpgradeState {
  learned: Record<PersonId, KnowledgeId[]>;
  productRecords: Partial<Record<ProductId, {
    source: 'prototype' | 'inspection';
    protocolIds: string[];
  }>>;
  commissionedSystems: SystemId[];
  instances: Record<string, {
    definition: SystemId;
    installedAssetIds: string[];
    profile: string;
    tasks: { taskId: string; assigneeId: string | null; priority: number }[];
    buffers: Goods;
    workInProgress: Record<string, number>;
  }>;
}
```

系统升级是选择后继系统节点并改造实例；不是任意切换一个无条件的自动化profile。原有可复用设备留下，新增设备和安装工作按差额支付；旧设施不用强制先拆光，也不同时保留双份产出。profile只选择该已建系统允许的配方和运行方式。

`productRecords` 和调试记录属于影响后续规则的事实。累计产量、节省人时、停机季数等统计由事件推导，不另写进GameState。实物必须有实例归属，同一台设备不能同时装进两套系统；退出系统需要先释放设备占用与在制品。

## 5. 人员配合：同一套任务预算，不新造行动点

“劳动量”是任务对时间与精力的报价，不是第三种可自由兑换的货币。任务同时要求岗位资格、时间、精力；搬运、机台操作、检验、维修可以有不同报价，不用一个全局效率系数缩放一切。

本人：使用既有每季12时间及实时精力。给系统预留任务后，对手动行动显示剩余可用预算；到结算时只有实际执行的任务才扣费，不能先把精力手动用光，再让预留工作透支。本人仍可取消尚未开始的安排或改派合格人员。

雇员：首版每个Worker增加独立可见的季时间额度、精力与岗位能力，工作耗能、恢复/休息占用其自身预算；额度与恢复是独立候选参数，不能默认为无限。暂不同时扩雇员婚育、完整寿命树；本人/后辈沿用已有人生规则。合同、资格、经验不等于免费产出。

一个人可做多个系统的任务，但预算共享；同一任务首版由一人执行，不能把两人的零散时间任意合成一次不可拆操作。可跨季建设/维修有明确在制进度，不满足条件的即时生产任务不消耗半份原料后消失。

工资建议采用完成的可计费工作时间，而不是“每个系统工作一次扣整季工资”；招聘成本保留，合同价目单显示最低计费单位。工资、时间和精力只结算一次，流水线减少实际工作量才减少雇佣支出。首版不同时叠加岗位费、系统管理费、个人工资三种重复收费。

调度建议以季内预算和显式任务先后顺序处理，不马上引入每日模拟。本人预留与手动操作共享设备和库存；供能→搬运→加工→交付等任务顺序必须可观察，资源刚产出可按顺序进入下游，但同一节点不能因循环供料无限重复执行。任务批数受季计划、设备容量和人员预算约束。

开工时原子校验并扣输入、工资、时间精力和设备容量；任何一项不足都不部分扣费。等待跨季的工序先扣开工成本，完成时只扣后续明确任务成本。无需求的灌溉任务不扣人力；缺水无法执行时不扣抽水成本，只有另行配置的巡检任务可正常收费。

## 6. 流水线、自动化与无人化

| 阶段 | 改变的任务 | 仍需要什么 |
| --- | --- | --- |
| 人工作业 | 人搬运、操作、检验 | 有限劳动、材料、手工具 |
| 机械化 | 降低操作精力或提高设备容量 | 人送料操作，能源与维护 |
| 流水线 | 合并重复装夹与搬运，连续衔接工序 | 稳定批量、标准部件、供料与少量操作检验 |
| 自动化 | 由控制和执行设备替代日常操作任务 | 能源、传感/控制设备、补料、检修和故障处理 |
| 无人运行 | 人工搬运、操作、检验、维修均有非人工替代 | 真实原料、备件、能源、自动物流与维护能力 |

流水线不是所有系统都必须经过的统一等级。机械加工适合流水线；灌溉更适合管网、阀控和巡检自动化，可以绕过加工流水线。两者在系统树中各走自己的分支。

无人化是边界声明：界面区分“本站无人操作”与“运行依赖链无人”。向有人供应商采购，只能算本站无人；若要宣称全链脱离人，水电、物流、备件供应与维护任务都不能依赖必需人工岗位。允许玩家决策开关系统，不为鼠标点击虚构一个经营者劳动岗位。

完全无人运行要能跨过至少一次正常维护周期。只从库存运行几季、零维护或关闭故障不算证明。自动维护设备不能要求先完成无人系统才能制造；允许前期由人或外部服务安装、调试和启动，达到无人运行后不再有必需人工任务。停电/断料导致无人系统停机是正常结果，不是“无人化失效”；物理成本仍存在。

首个实现不强制加入随机事故。先用确定性的磨损与维护任务验证无人闭环，避免没有解释的随机停机掩盖供需问题。

## 7. 与现有代码的落地边界

1. 保留19个K节点，删除学习样品硬前置；不先扩全学科。
2. 增加P的定义、产品验证和制造规程；重新审核现有`from`。配方继续描述物资变化，不当成知识节点。
3. 将供水、加工相关副作用移入S实例。删除旧效果入口的重复结算，不能新系统运行一次、旧泵逻辑又灌溉一次。
4. 给本人和雇员提供统一任务报价、预留和季预算。原岗位按季收费与新按工作量收费不可混用。
5. 先接手动/机械化两个系统与明确劳动削减；后期自动化仅在必要设备与维护依赖定义完整后开放。
6. `observeSession()`显示解锁缺项、实物占用、各任务人力、计划及实际扣费、停机原因；不暴露种子、随机状态、寿命秘密或未来天气。
7. `src/game/game.ts`仍是唯一权威；领域层不得依赖runtime、agents、research或apps。

候选落地版本暂称0.19.0；仅实际改规则时递增版本，不在本轮改package或rulesets。采用新局，不把0.18的免费自动效果、雇员经验、验证记录直接猜测迁移成新岗位；历史档案及报告保留。未来如需迁移必须另列逐字段映射与指纹策略。

## 8. 风险与后续最小验证

| 假设 | 反例/风险 | 未来验证方式 |
| --- | --- | --- |
| 三类树更清晰 | 产品逐个验证让总链反而更长 | 比较首次收益前的总依赖、试制次数与个人投入，不能只统计K深度 |
| 产品验证长期保留 | 外购检验使全链自制没有价值 | 分开比较自制与购入检验的资金、劳动、供货约束及规程收益 |
| 系统减重复操作 | 岗位设置比点旧按钮更繁琐 | 两个系统提供默认任务模板，一次配置后持续运行；检查调整次数 |
| 流水线减少用工 | 减人数却叠加固定费用，实际负担增加 | 固定相同产量比较工资、人时、能源、损耗、停机和资本回收 |
| 人工预算统一 | 预留与手动操作重复占用或透支 | 同人两系统、途中撤销、缺料/缺款、同台设备竞争的边界检查 |
| 跨代可以接续 | 强制后辈重学全树才能开旧厂 | 交接后旧规程可运行，新研发仍需个人K；缺合格岗位应明确停机 |
| 自动化最终无人 | 没人操作但隐藏人工补料维修 | 无人工分配，跨维护周期，检查全部运行依赖及实际事件 |

进入实现后的最小检查：先做因果/接口单元检查，再对供水与机械加工各用一个固定场景和同一种子成对检查；比较只改变一个运行方案，保持需求、初始资产、库存和劳动策略一致。专用测试夹具须明确标记为场景构造，不冒充从正常开局。之后各做一条有限正常开局可达性记录；如果失败，仅复核受影响部分。自动化有实现后再测，不现在造虚假结果。

接受门槛：无解锁环、无资源/工资/劳动重复结算、停机原因可解释、产品前置确有用途、至少一个升级能在相同有效产出下降低实际人力。是否改善长期资金节奏另行判断，不能因机制通过就宣布平衡完成。本轮仅做下文静态推演，尚无新规则运行证据。

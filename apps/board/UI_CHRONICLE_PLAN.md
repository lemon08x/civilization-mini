# B 方案：家族编年史游戏界面实施方案

状态：设计已选定，实施待开始。本文是本 PR 相对 main 的第一笔提交。

用户选择 B「家族编年史」，要求先开 PR，把完整实施方案放在第一笔提交，后续交给 grok4.6 模型 agent 实施。本次只交付方案，不实施 UI、不启动后续 agent、不合并 PR。用户此次请求明确授权本方案文档；不因此扩大其他文档、测试或研究内容的新增范围。

设计基线：2026-09-18，main `9cc9e28`，规则 0.27.0。实施前重新核对分支和变更，不把此哈希当作永远最新的规则。

## 1. 玩家问题与完成目标

目前生活、学堂、制造、人员和社会结算各自能操作，但玩家需要在许多面板间拼接“这一季的生活是否稳妥、下一步能做什么、这代留下了什么”。新界面用一本正在续写的家族编年史组织这些事实，让人物与季节成为主线，同时保留完整经营信息和行动入口。

类型为**呈现与界面交互改造**，世界结果不变。完成标准是用户能从开始界面进入真实存档，完成现行行动、查看反馈、推进季节、理解交接和阶段结算；不是只交付静态页面，也不是只给原页面换颜色。

## 2. 范围与硬边界

- 主范围：`apps/board/` 的现有网页入口、外壳、页面、状态反馈及 CSS；继续使用现有 TypeScript、HTML、CSS 和本地 HTTP 服务。
- 根 `AGENTS.md` 始终适用。默认在本 PR 分支继续工作，不另开实施 PR 或切换到 main。
- 不改 `src/game/` 机制、规则 JSON、数值边界、存档形状或版本；不扩张 `src/runtime/`；不改 CLI / AI 玩家入口。
- 不引入 React、构建框架、外部图标/字体 CDN、新依赖、图片生成服务或付费 API。沿用 `ui-icons.ts`，视觉首先由排版、留白、线条与现有图标完成。
- 不新建测试、实验、脚本、研究层或额外设计文档。必要的页面组件可在 `apps/board/` 保留范围内拆分，优先复用现有文件。
- 不扩展旧作坊、远征、试炼等当前观察没有开放的子系统；存在文件不表示玩家可用。
- 不新增家谱模拟、人物故事生成、成就评分、任务系统、自动决策、时间轴存档字段。
- 如发现必须改机制或新增公开观察字段才能完成的部分，在本 PR 说明具体缺口并等待另行授权；先完成已有观察能支持的呈现，不绕过边界直接读内部状态。

## 3. 已选视觉与信息架构

### 3.1 B 的设计方向

整页像一本可操作的家族记事册。暖纸色、大标题、章节引语、横向篇章导航、细线分区构成主要识别特征。避免把所有信息做成一排排等权重仪表卡，也不保留 A/B/C 方案选择器。

桌面结构：

```text
世代 / CIVILIZATION MINI        当前家族 · 社会阶段        存档与帮助
本季  生活与家人  学习与制造  经营与交易  社会历程
──────────────────────────────────────────────────────────────
第 N 代 · 第 Y 年 · 春 · 当前天气
可用时间 / 总预算      可用精力      可食储备 / 季耗      钱财
──────────────────────────────────────────────────────────────
篇章眉题 / 真实人物与阶段上下文
把日子安顿好，才有余裕向前。
当前页标题与必要说明

主要阅读区（约 2/3）               当下关注 / 选中项（约 1/3）
田地 / 课程 / 配方 / 家人           条件、报价、阻碍、实际行动

本次变化 / 最近记事（真实事件）
──────────────────────────────────────────────────────────────
季末检查摘要                       [结束本季]
```

- 导航先按现有 `playerGroups()` 重组为少量横向分组，再在组内选择具体页面。不可用预览的六个过程按钮替代全部游戏功能。
- “本季”和“社会历程”可分别映射聚落、社会；生活组保留田地、生活、家人、仓库；学习组保留学堂、产品研发、加工；经营组保留现行系统、集市、供能等条件页。
- 社会可从现有分组提升为顶级入口，但不得同时维护两份冲突的导航定义。保留 `data-page` 的内部页名，显示名称可优化。
- 当前页、二级导航、章标题保持一致；课程选择、集市筛选和未提交表单在普通重绘时不意外丢失。
- 春夏秋冬、人物代次与社会阶段是不同维度，不把换季、换代、进入下一社会画成同一进度条。
- 六个预览章节是设计情境，不是所有玩家必须依序完成的六步任务。文字只表达氛围，不宣布虚构成果。

### 3.2 视觉规格

| 项目 | 实施规格 |
| --- | --- |
| 页面底色 | `#efe9df`，正文纸面 `#fffcf5`；作为 CSS token 集中管理 |
| 主文字 / 次文字 | `#283b31` / `#626e61`；小字确保实际背景上清晰可读 |
| 主色 / 柔和强调 | 棕色 `#7b4d35` / `#eee0d0`；重点按钮为深棕底浅字 |
| 分隔 / 警告 | `#ded0bf` / `#8a5426`；危险操作另用克制的红褐色，不靠颜色单独说明 |
| 字体 | 标题用 Georgia、Noto Serif SC、SimSun、serif 回退；正文 Microsoft YaHei、sans-serif；不下载字体 |
| 字号 | 页面章标题 28–32px；段标题 16–18px；正文 14–16px；辅助文字不少于 12px |
| 尺寸 | 桌面内容最大约 1280px；正文可读行长优先；双栏约 2:1，详情栏至少 280px |
| 间距 | 以 4/8px 为基准；块间 20–28px；不靠巨大空白制造篇章感 |
| 容器 | 阅读区尽量开放，用细分隔线；仅行动详情、提醒、确认面板使用实底；圆角 4–8px，少用阴影 |
| 数字 | 资源用等宽数字对齐，单位紧邻；警告与可执行状态同时给文字 |
| 动效 | 可选 120–180ms 状态过渡；尊重减少动态效果设置；不做循环装饰或翻页阻塞 |

优先实现完整浅色 B 方案，不要求增加主题切换器。若继承现有深色适配，全部 surface/text token 成对定义，不能只反转背景。此项不是扩大第一版范围的理由。

响应式：约 900px 以下收拢主次栏，600px 以下单列，资源 2×2；导航可换行或仅在局部横向滚动，页面不得横向溢出。详情不能盖住主要内容；主要行动至少约 44px 点击区，320/390px 宽仍能读清成本和不可用原因。桌面必要时可用不遮挡内容的粘性操作条；移动端优先自然文档流。

### 3.3 控件与状态规范

- 每组只有一个最主要行动；查看规则、展开条件、返回页面使用次级文字按钮。
- 行动统一展示 label、时间、精力及已报价的钱/粮；零成本与缺失字段区分。说明与不可用原因无需悬停即可阅读。
- 已掌握、可执行、待前置、阶段未开放、执行中、失败、完成使用明确文字，不能只换颜色。
- 正在提交时立即阻止重复点击；成功后重读观察更新资源和详情；失败保留上下文和原存档，不显示假成功。
- 普通行动不增加确认弹窗。阶段结算、交接等后果较大的操作，先展示具体后果，再由用户提交原有行动。
- 原生按钮、标签、进度和 details 优先；如用对话框，支持 Esc、键盘焦点管理、关闭后回焦与移动端布局。
- 状态反馈使用适度的 `aria-live`，错误用 `role=alert`；焦点轮廓不能去掉；全量重绘后恢复合理焦点，不跳回页顶。

## 4. 数据与行动契约

### 4.1 唯一数据流

```text
当前 session → observeSession(session) → 页面呈现 / 局部 UI 状态
用户确认真实行动 → submitCommand(session, command)
                 → game.ts transition → 保存新 session → 再观察、重绘
```

页面读取 `SessionObservation`，不直接读取 `session.state` 推导结果。业务数值、可执行性、报价与阻碍来自观察及 `game.actions`。不能把截图示例数值、规则说明里的常量写成运行值。

`economy-app.ts` 保留调度职责；页面函数只消费观察、选择状态和统一行动渲染器。导航、展开、查看预览不提交行动。命令继续使用当前 runId、revision 和 actionId；沿用 busy/failed 保护、写档错误处理与解析版本校验。

选择页面、选中课程、弹窗是否打开、上一行动反馈属于 UI 状态，不写进世界状态或修改存档格式。若缓存相邻两次公开观察计算变化，只能展示实际前后差值，不对未来执行 transition 作模拟。

### 4.2 数据入口映射

| 呈现 | 当前公开来源 / 接入位置 |
| --- | --- |
| 代次、年份、季节、当前天气 | `game.clock`、`game.life.calendar`、`game.world.weatherName` |
| 时间、精力、预留 | `game.life.budget`、`timeRemaining`、`timePerSeason`；总量与可用量分开 |
| 粮食与钱 | `economy.foodTotal`、`parameters.foodPerTurn`、`socialFood` 报价、`family.money` |
| 田地与库存 | `economy.field`、`harvest`、`goods`、`storage`、现行商品/作物目录 |
| 人物与后辈 | `game.life.person`、`heir`、`pendingRetirement`；已有天赋、健康、年龄等 |
| 分支课程 | `economy.branchView.nodes/paths`；`branch-view.ts` 已有选中课程与前置逻辑 |
| 产品、实物、验证、规程 | `economy.industryView`、`economy.products/processes/equipment` |
| 系统、人力与工资 | `economy.industryView.systems/workers/reserved`、`staff`；真实 blockers |
| 供能 | `economy.modern`、`electricView`、设备耐用与当前行动报价 |
| 阶段、回报、最终副本 | `game.era` 的 `projection/expectedReward/electricRewardPercent/dungeon` |
| 最近行动 / 历次阶段结算 | `SessionObservation.recentEvents`、`eraSettlements`；既有 `feedback()` |
| 实际可用行动 | `game.actions` 的 id、label、enabled、reason、description、报价字段 |

实施时以真实类型为准，条件字段先判空。目录用于解释名称，不能替代观察来判断资格或资源。只存在旧代码而观察缺失的功能，不渲染可点击入口。

### 4.3 编年史不是新事件存储

首版“记事”只展示公开观察可见的最近事件、已结算社会和当前家族事实。不从种子、随机状态、原始未来状态编写故事，不杜撰人物姓名、寿命、亲缘和已发生的里程碑。

`recentEvents` 范围有限，不能声称有完整跨代历史。页面可写“最近记事”“社会历程”，不得伪装成完整家族档案。现有事件文案可改善排版并做确定性摘要，但不能依赖外部模型生成物理结果。

## 5. 页面实施要求

### 5.1 入口、开始与存档

- `/`、`/start`、`/play` 统一 B 视觉。开始界面以“开启家族旅程 / 打开已有旅程”组织现有新建与存档列表。
- 保留环境选择及现有种子设置能力；种子不进入游戏 HUD、记事或策略观察。
- 仍由玩家选择打开或新开，禁止启动时自动进入上一局。
- 保留导入导出与错误提示。版本不支持、文件损坏、写档失败时保护原档；不要因重构开始页增加覆盖存档行为。
- `/ai` 仅保持样式兼容与现有导航可达，不改 AI 协议或玩法。

### 5.2 日常经营 / 本季

主区呈现当前人物、季节、田地状态；次区呈现生活缺口、自由时间与真实需要注意的事情。章引语可以是固定氛围文字，但不得替代信息。

- 固定 HUD 的粮食不只看存粮：结合预计购粮、成本、剩余缺口判断；零库存不能直接标成断粮。
- 田地显示作物、生长、肥力、供水、预计收获；预计与实际清楚区分。
- “接下来可做什么”最多列少量当前可用行动或功能入口，不内置策略评分，不自动执行，不称为最优建议。
- 空田、作物生长、成熟、缺粮、预算不足都要有明确状态和可达的处理入口。
- 仓库、生活政策、公共食品、休养等原功能仍在组内页面，不能为了主页简洁删除。

### 5.3 学堂与产品研发

采用“课程目录 + 阅读页详情”的 B 排版。以当前 `branchView` 为准，呈现分叉、前置、时代有效性、已掌握、传承、记录与教导。

- 不照搬初步预览的通用“证据 → 下一阶”。现行分支课程按前置和行动报价学习，不新增通用实验门槛或样品费用。
- 保留当前 `selectedCourse`、`data-course`、前置跳转和渠道/工艺入口。
- 展示后续课程时不能用“已掌握数量”误导玩家集齐即可胜利；其他社会课程、历史记录与本阶段生效状态须区分。
- 产品页分别显示：实物库存/耐用、验证记录、制造规程。购买实物不赠送规程，检验也不能被展示成自动获得规程。
- 研发、试制、检验、运行验证、制造等真实行动按当前观察开放；不把产品关系图误当必须依次造过全部产品。
- 原料、设备、个人知识和验证条件就地列明；用通往现有集市/学堂的导航帮助处理缺项。

### 5.4 加工、系统、人员与交易

以记事册中的“家业”篇呈现实际生产。配方内容按“投入 → 工序 → 产出”阅读，但保留 B 外壳，不把整个应用改成 C 仪表台。

- 加工显示配方、批量含义、设备占用、开工投入、即时/跨季完成、本人在制品和完成行动。
- 系统呈现建设、调试、人员安排、运行各状态，区分手动本季操作与既有持续任务。
- 人员预算、本人预留、工资、设备耐用、真实 blockers 明确显示；缺料不能呈现正在生产。
- 当前 `industryView` 下的本人播种/收获、手动采购/交付不得写成免费托管；不因旧 `operations-view.ts` 有开关而复活无人生产。
- 继续支持招聘、人员安排、释放预留、暂停/撤除等既有操作；按真实 action.enabled 显示资格。
- 集市保留类别、筛选、清单、整单结账、库存/运输、现货/次季订单、维修等现有入口。不能把跨季到货画成即刻到账。
- 工资、食品、运输、在途库存相关提示只显示观察支持的事实，不在 UI 再实现采购算法。

### 5.5 供能 / 灯亮起来的晚上

把发电、消费、剩余与储能组织为可读流程，设备列表保留安装、启用、耐用、本季运行状态。

- 安装、开关启用、本季实际运行是三种状态；点击启用不能显示发电成功。
- 调度必须提交现有 `economy:energize:now`，并显示当前时间/精力报价；按观察反映水电、燃料、储能及负载顺序。
- 水电当前天气产能、公共水/燃料、耐用与当季额度来自实际数据；不能固定展示“6 电”。
- 电灯加时、调度耗时与精力同时体现；服务不提供无限重开额度。
- 电报只影响本季新订单；不能宣称加速已有订单、维修或培训。
- 电解槽按批加工，无启停开关。导线配方及原料来自目录，不重算工业公式。
- 余电、可储存量、季末耗散提示来自观察；不能写成所有电力都无法跨季保留，也不能季末自动发电。
- 现代回报条件依据真实电器运行，不能用“有设备/已启用/已发电”代替；具体比例来自 `electricView` / `era`。

### 5.6 家人、传承与交接

两代人物在同一阅读跨页中比较，展示年龄、天赋、健康、精力与已知学习状态；不需要画像资源或多代虚构家谱。

- 未有后辈、未成年、已成年、不可继任、待季末交接、已交接、家族结束分别呈现。
- 点击交接前展示当前真实条件、哪些家业保留、哪些个人理解仍需学习；提交真实退休/交接行动。
- 使用 `pendingRetirement` 和当前状态区分“已安排”与“已完成”，不能提前切换人物。
- 家族契约与安排是否接续只在观察支持时展示，不硬编码“必定自动接续”或套用旧版组织 3 阶规则。
- 真实交接后可展示一次内嵌章节转场，清楚显示新经营者和实际变化；关闭回顾不再提交行动。
- 休息、疗养、教导、记录等既有操作保持可达。死亡或终局只读呈现，保留导出与回到开始的入口。

### 5.7 季末、社会阶段、最终结局

三个概念分开：结束本季、结算当前社会、结束现代旅程。它们不能共享含糊的“下一章”行动按钮。

- “结束本季”先展示**当前条件检查**：生活报价/缺口、已预留任务、已知停机原因、待交接、未储存电等。没有观察支持的未来粮钱健康精确值就不展示，不复制季末结算器。
- 确认时提交 `economy:end:season`；最新真实事件形成回顾。天气等变化只在结算后出现。
- 社会页保留当前阶段、剩余季数、社会卡、公共服务、课程开放及历史回报。
- “结算当前社会”使用 `economy:erasettle:stage`，后果面板显示当前 `expectedReward`、已得凭证、剩余产能推算及 notes；强调它会结束本季并进入下一社会，现代则结束旅程。
- 预估会受当季实际结果影响，最终金额以真实结算事件为准；UI 不重新计算回报公式。阶段到期的自动结算也要通过事件显示。
- 最终副本来自 `game.era.dungeon`，在社会/最终章节内显示；不要与旧 `economy.expeditionView` 混用。
- 显示进度与通电验收两个条件，交付使用实际行动，不能只因为进度满或拥有电器就宣布完成。
- 区分副本条件达成、现代结算后旅程胜利、未完成副本而主动结束、家族经营失败；以实际终局观察和事件为准。
